## ak update

Preview or apply AgentKit-owned project refreshes

### Synopsis

Update AgentKit: on an interactive TTY, bare `ak update` runs a step-by-step wizard (CLI signed self-update → global/user kits → project kits). With --yes (or after an interactive accept) it updates or re-executes the ak binary first when needed, then refreshes kit content. Use `ak self-update --yes` for a binary-only operation. Each step defaults to N; pass --yes to accept every step, or pin scope with --global / [project-dir].

Project scope: for each tracked file, `ak update` checks whether the user has modified it since install. Clean files are overwritten; user-modified files are skipped (unless --force). Every run snapshots the exact files it writes or prunes before mutation; --force, --backup, or backups.enabled: true in ~/.agentkit/config.yaml captures the whole project instead. --no-backup skips the snapshot. After the tracked kits/ tree, a project update also refreshes every installed runtime of each project kit (.claude, .codex, adapter roots), one pass per kit and runtime through the same path as `ak kit refresh`; a failed pass does not stop the others, and each pass reports its own row. A project with only runtime installs refreshes those. Preview and --dry-run list the planned runtime refreshes without writing.

Scripted / non-TTY callers without --yes stay preview-only (exit 3, offline-safe). Pass --global (-g) to refresh only AgentKit-owned user/global kit installs (preserve-only; no --force). Claude Code user-plugin-only installs are reported, not silently refreshed — use `ak kit refresh <kit> --global --switch-to-plugin`.

Runtime selection: --target (alias --runtime) picks which agent runtime(s) to update. Project remote targets: claude-code, codex, cursor, dsh, grok, omp, pi. Global remote targets: claude-code, codex, cursor, dsh, grok, omp; global local-source targets: claude-code, codex, cursor, dsh, grok, omp. In both scopes it filters which installed runtimes refresh — unset means all discovered runtimes; a runtime you ask for but have not installed in that scope is reported as skipped, not an error. The project kits/ tree still comes from one runtime's download: claude-code when it is selected or installed (or nothing is selected), otherwise the first selected runtime. --target and --runtime are the same flag; set only one.

Background auto-update (opt-in, off by default): --schedule daily|weekly makes the first `ak` command after each interval start a detached update of the CLI and global kits, plus every project opted in with --project &lt;dir&gt; (it must be registered with `ak projects add`) whose git tree is clean and has no live agent session. --no-project &lt;dir&gt; opts a project out, even if its directory is gone. --schedule off stops it and clears its state. --status [--json] shows the schedule and the last result without changing anything; --ack also marks that result as seen. These settings flags write only the auto_update: section of config.yaml, update nothing now, and cannot be combined with the update flags or a project-dir argument. A background project update refreshes only the tracked kits/ tree; it never refreshes project runtime installs and logs a notice to run `ak update <dir> --yes` or `ak kit refresh <kit>` instead. Background updates never start when AK_NO_AUTO_UPDATE=1 or CI is set; AK_NO_AUTO_UPDATE=1 also stops a kit minimum from replacing ak implicitly, and a build without a release semver is never replaced automatically.

SSOT upgrade (opt-in): --ssot moves the kit skills installed in the global scope and in this project (--global: global only; --all-projects: every registered project too) into the content-addressed skill store of AGENTKIT_HOME, through the same plan, lifecycle lock and journaled transaction as `ak skills migrate`. It adopts files as they are on disk and never rewrites, moves or removes a skill file: a modified, unlisted, linked, colliding or divergent skill stays a legacy install and is reported as skipped with its reason, and skill aliases (and their ak:&lt;slug&gt; invocations) are unchanged. Runtimes the store does not project yet and plugin-delivered kits are reported, not migrated. --dry-run prints the plan and readiness with no write and no network request. Without --yes the plan is a preview; an interactive terminal may confirm it, --json and non-interactive runs never prompt. An apply first takes a protected pre-upgrade checkpoint (--backup-sessions adds session history) and stops before any change when it fails, migrates each scope, re-plans to verify it converged, writes a receipt under AGENTKIT_HOME/state/upgrades/, and only then commits the store mode for those scopes. Each scope keeps its own mode: the global scope covers global operations only, and a project uses the store only when that project was upgraded (an explicit AGENTKIT_SKILL_STORE wins; a v2 rollback hold turns it off). An interrupted upgrade is resumed with the same checkpoint and scopes by the next `ak update --ssot` or an applying `ak update --yes` whose flags are valid (its --json payload reports ssot_resume); scope flags naming other scopes exit 2 until it finishes. --force, --no-backup and kit-source flags are refused with --ssot. Undo with `ak rollback --to v2`.

Effects:
  TTY wizard applies only the steps you accept (or all steps with --yes). Scripted project updates preview by default; apply with --yes. With --yes (and after an interactive accept), the command updates or re-executes the ak binary first when needed, then refreshes kit content. CLI hard-gate runs before kit mutation (manager-owned / Windows-pending / restart-required abort). Kit failures continue with an honest summary and a support bundle under ~/.agentkit/support/. Global refresh is preserve-only: --force never overwrites user-modified files; it only authorizes archiving legacy ClaudeKit Codex skills so the refresh can proceed. Use `ak self-update --yes` for a binary-only operation.

Exit status:
  0   success
  1   runtime error, CLI hard-gate, partial kit failure (including a failed project runtime refresh pass), or interrupt after mutation; for the auto-update settings and --status --ack, an I/O failure or a busy state file
  2   invalid flags (including --target with --runtime set differently, or an unknown runtime); at project scope: no tracked kits and no runtime install, or a --target that matches no project runtime install; with --global: a project directory argument, an empty refreshable set, or a plugin-only result; for the auto-update settings: an invalid --schedule, an unregistered --project, or a settings flag combined with an update flag
  3   preview only — neither --yes nor an interactive confirmation was given
  4   --ssot: the host or file system cannot run the skill store (unsupported OS, no file locks), or another AgentKit operation holds the kit lifecycle lock or the backups lock
  6   --ssot: a preflight blocker refused the upgrade before any write (the JSON error remediation names its code, impact and fix), the checkpoint did not fit on disk, or the migration met a conflict
  7   --ssot: the migration refused a link or untrusted path inside a skills root
  15  renewal_required: the registry refused a kit release the update window does not cover; installed versions keep working, and the JSON error names the latest covered version and the renewal link

```
ak update [project-dir] [flags]
```

### Examples

```
  ak update ./myproj --yes
  ak update --schedule daily --project .
  ak update --status --json
  ak update --ssot --dry-run --json
```
