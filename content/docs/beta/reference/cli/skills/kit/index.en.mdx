---
title: ak skills kit
description: Preview, apply, rebase, roll back, publish and sync personal kits that extend exact kit versions with overlays and forks.
---

Use `ak skills kit` to work with personal kits. A personal kit `local/<name>`
extends exact kit versions with overlays and forks; its manifest is
`AGENTKIT_HOME/kits/personal/<name>/personal-kit.yaml`. The commands project the
resolved composition into the native skills roots, owned by `personal:<name>`,
in one journaled transaction. Running the group command prints help and exits
`0`.

## Usage

```bash
ak skills kit <command>
```

The group accepts no positional arguments and has no flags of its own. Shared
flags are described in [CLI conventions](../cli-conventions).

## Requirements

The group is registered by default; `AGENTKIT_SKILL_OVERLAYS` set to anything
but `1` hides it. What each subcommand needs:

| Need | Commands |
| --- | --- |
| Nothing: offline, for every user | `status`, `inspect`, and the `--dry-run` of `init`, `new-skill`, `resolve` and `rebase` |
| The skill store | `apply`, `rollback`, `remove` and `sync` (dry runs included), plus `init`, `new-skill` and `resolve` |
| SkillX | `publish`, `revisions` and `sync` |

Both the skill store and SkillX turn on after `ak update --ssot`, or with
`AGENTKIT_SKILL_STORE=1` and `AGENTKIT_SKILLX=1`. `init`, `new-skill`, `resolve`,
`publish` and `revisions` only touch `AGENTKIT_HOME` and follow its global scope from any
directory; a projection follows `--scope`. An upload needs an unscoped SkillX
API key in `ak secrets` (`SKILLX_TOKEN`).

## Subcommands

| Command | Outcome | Disk effect |
| --- | --- | --- |
| `ak skills kit status [name]` | Show whether personal kits resolve against their foundations. | Read-only. |
| `ak skills kit inspect <name>` | Show the resolved composition plan. | Read-only. |
| `ak skills kit init <name> --extends <kit>@<version>` | Create a personal kit manifest. | Writes the manifest. |
| `ak skills kit new-skill <kit> <alias>` | Add a brand-new skill, authored in the personal kit. | Writes the manifest and the skill's `skills/<alias>/` tree. |
| `ak skills kit apply <name>` | Project the composition into the skills roots. | Writes the skill store, skills roots, lock and receipts. |
| `ak skills kit rebase <name> --to <kit>@<version>` | Preview or apply a move to a new foundation version. | Dry run is read-only; an apply projects, a stopped rebase writes its conflict report. |
| `ak skills kit resolve <name> --path <path> --choice <choice>` | Record the user's resolution of a rebase finding. | Writes resolution records and the kit's own files. |
| `ak skills kit rollback <name>` | Project the previous revision again. | Same transaction as apply. |
| `ak skills kit remove <name>` | Drop the kit's projections. | Same transaction as apply. |
| `ak skills kit publish <name>` | Upload the kit's delta to SkillX as a revision. | Writes the SkillX link record. |
| `ak skills kit revisions <name>` | List the kit's SkillX revisions. | Read-only. |
| `ak skills kit sync <name> --locked` | Project one exact SkillX revision. | Same transaction as apply, plus the link record. |

A plan that needs review is applied only with the plan token the user approved.
The projecting commands never rewrite the personal kit or the foundation kits,
and never run a script.

## Add a new skill

`ak skills kit new-skill <kit> <alias>` creates a skill that has no foundation:
its identity is `@local/<alias>` and the personal kit `local/<kit>` is its only
source. It is not a fork, so a [rebase](./rebase) never touches it. The
personal kit must already exist ([`ak skills kit init`](./init)).

```bash
ak skills kit new-skill mine my-tool
ak skills kit new-skill mine my-tool --description "Use when ..." --dry-run --json
ak skills kit new-skill mine my-tool --from-dir ./drafts/my-tool
```

| Flag | Default | Description |
| --- | --- | --- |
| `--from-dir <dir>` | none | Copy an existing skill directory instead of scaffolding one. It needs a `SKILL.md`; the `name` in its frontmatter is set to the alias. |
| `--description <text>` | a placeholder | One-line description of the scaffolded `SKILL.md`. Ignored with `--from-dir`. |
| `--kits-dir <dir>` | `$AGENTKIT_KITS_DIR` or `./kits` | Foundation kits directory. |
| `--dry-run` | `false` | Print what would be written and write nothing. |

The alias uses kit ID characters (lowercase letters, digits and single
hyphens), must not start with `ak-` (reserved for AgentKit's own skills), and
must not repeat an identity or alias the kit already provides.

Without `--from-dir` the command scaffolds a minimal `SKILL.md`. A copied
directory is checked like any personal kit tree: no links or special files,
the skill tree size limits, and a `SKILL.md`. A tree that carries a secret or
an absolute local path is refused with `personal_kit.payload_refused` and exit
`7`; nothing is written, and the message names the rule, never the matched
text.

Without `--dry-run`, under the kit lifecycle lock and after store recovery,
the command writes the manifest and the whole `skills/<alias>/` tree in one
journaled transaction. An existing `skills/<alias>/` directory is refused with
exit `6`, and a manifest changed since it was read stops the write, so nothing
is overwritten. The command never projects: run
[`ak skills kit apply <kit>`](./apply) next, which the output prints as
`next:`.

The new entry appears in the `skills:` list of
`AGENTKIT_HOME/kits/personal/<kit>/personal-kit.yaml`:

```yaml
skills:
  - identity: "@local/my-tool"
    alias: my-tool
    dir: skills/my-tool
```

`identity` must be `@local/<alias>` and `dir` must be `skills/<alias>`. The
tree's `SKILL.md` `name` must equal the alias. A local skill's trust is
`local-unverified`.

JSON uses `kind=skills.kit.new-skill` with these fields under `data`:

```text
dryRun, personalKit, identity, alias, dir, source, files[],
compositionDigest, exposure, scripts[], renamed, manifest, next
```

`source` is `scaffold` or `from-dir`, and `renamed` is `true` when a
`--from-dir` `SKILL.md` name was set to the alias.

### Improve, roll back and publish a local skill

- [`ak skills improve @local/<alias>`](../cli/ak_skills_improve) resolves its
  base from the personal kit. [`ak skills evolution apply`](../evolution/apply)
  rewrites `skills/<alias>/` in place, and
  [`evolution rollback`](../evolution/rollback) restores it byte for byte. These
  files are written with mode `0644`.
- [`ak skills kit publish`](./publish) refuses a kit that holds a local skill
  with `kit.local_skill_unsupported` and exit `10`, before anything is sent.
  SkillX cannot accept a skill without a foundation yet. The skill stays usable
  locally through `ak skills kit apply`.

## Output and exits

Each subcommand writes human output or one JSON envelope. JSON kinds are
`skills.kit.status`, `skills.kit.inspect`, `skills.kit.init`,
`skills.kit.new-skill`, `skills.kit.apply`, `skills.kit.rebase` (dry run), `skills.kit.rebase-apply`,
`skills.kit.resolve`, `skills.kit.rollback`, `skills.kit.remove`,
`skills.kit.publish`, `skills.kit.revisions` and `skills.kit.sync`. Each page
lists its exit codes; the read-only and projecting commands share these:

| Exit | Meaning |
| --- | --- |
| `0` | Success, or nothing to change. |
| `1` | Command failure; for `status` and `inspect` also an overlay conflict, shared alias, alias collision or stale proposal. |
| `2` | The skill store disabled, invalid flags or arguments, or a malformed manifest, overlay or proposal. |
| `4` | Another AgentKit operation holds the kit lifecycle lock (projecting commands). |
| `5` | Personal kit, foundation, version, skill or previous revision not found. |
| `6` | Review required, stale plan token, rebase conflict, alias collision, or an unowned or modified path (projecting commands). |
| `7` | Revoked foundation, a link in a target path, or a digest mismatch. |
