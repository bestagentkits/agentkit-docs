Use `ak setup` to detect locally available runtimes and save AgentKit adapter
and default-kit preferences. Basic setup does not sign in to the AgentKit
registry or install kit content, and it does not change telemetry: telemetry is
disabled by default on every release channel, and basic setup keeps whatever
choice is already stored. To opt in or out, run `ak setup --step telemetry` or
`ak setup --advanced`.

## Syntax

```bash
ak setup [options]
```

## Arguments

The command accepts no positional arguments and has no aliases.

## Before you run

Interactive setup needs terminal input and output. In automation, select
adapters explicitly or provide a YAML answers file:

```bash
ak setup --adapter claude-code,codex,cursor,dsh,grok,omp,opencode,pi --no-interactive
ak setup --config setup.yaml --no-interactive
```

Basic setup detects native runtime login state but never copies runtime
credentials. `--advanced` can store provider keys in
`~/.agentkit/config.yaml`; the file is written with mode `0600`, but the keys
remain plaintext and must be protected as secrets.

Selecting `dsh` or `grok` records the enabled-adapter preference and checks whether the
local binary resolves. It also enables that runtime as a Kit projection target. Setup does not install Kit packages, probe or write DeepSeek Harness
or Grok authentication, or choose a runtime model; Kit installation uses the signed remote
registry by default unless you explicitly choose `--local --kits-dir`.

Selecting `opencode` checks only that the `opencode` binary resolves (or
`AGENTKIT_OPENCODE_BIN`); OpenCode keeps its own provider credentials, set with
`opencode auth login`, and setup never reads them. OpenCode is a spike adapter
with no released Kit package, so install Kits for it from a local source with
`ak kit init --local --kits-dir <dir> --target opencode`.

## Options

| Option | Default | Description |
| --- | --- | --- |
| `--adapter <ids>` | Current `adapters.enabled` | Set the enabled adapters to a comma-separated set of registered adapters: `claude-code`, `codex`, `cursor`, `dsh`, `grok`, `omp`, `opencode`, or `pi`. The list replaces `adapters.enabled`, so adapters you do not list are disabled; `none` disables every adapter, and an empty value is refused. `dsh` and `pi` also act as Kit projection emitters (`ak kit init --target dsh`, `ak kit init --target pi`); listing `pi` here does not provide `ak run --target pi`. |
| `--no-adapter <ids>` | Empty | Disable a comma-separated set of those registered adapters. With `--adapter`, it filters that list; used alone, it removes them from the current `adapters.enabled` and keeps the rest. |
| `--advanced` | `false` | Include provider keys, provider/model preferences, and Codex overrides. |
| `--config <path>` | Empty | Read scripted answers from a YAML file whose keys are setup step IDs. |
| `--step <id>` | Empty | Update one setup field instead of processing the complete step set. |

Without `--adapter`, `--no-adapter`, or an `enabled_adapters` answer in
`--config`, setup keeps the current `adapters.enabled`; a first run picks a
default. When the new selection disables an adapter that was enabled before,
setup prints a warning on stderr that names the previous value, the disabled
adapters, and the command that restores them
(`ak setup --adapter <ids> --no-interactive`).

Unknown step IDs and conflicting adapter selections fail before configuration
is written. See [CLI conventions](../cli-conventions) for shared flags such as
`--json`, `--no-interactive`, and `--quiet`.

## Examples

Run the terminal wizard:

```bash
ak setup
```

Update only the enabled adapters:

```bash
ak setup --step enabled_adapters
```

In the wizard, the adapter step is a multi-select pre-checked with the current
adapters. Selecting none stores `none`.

Apply a scripted file and return structured output:

```bash
ak setup --json --no-interactive --config setup.yaml
```

## Terminal and scripted behavior

When stdin and stdout are terminals, the default command opens a wizard.
Pressing Esc or Ctrl-C cancels before saving and exits `3`. `--json`,
`--no-interactive`, or non-terminal output selects the scripted path instead;
missing required values then exit `2` rather than opening a prompt.

The command has no dry-run, apply, force, or confirmation flag of its own. A
successful scripted invocation writes immediately. Re-running is idempotent and
keeps existing values for steps you do not change.

## Output and streams

Human success output goes to stdout. It reports native runtime and AgentKit
session state, the saved config path, and applied step IDs. The interactive
wizard and cancellation/error messages use the terminal and stderr as needed.

JSON success is one envelope on stdout:

```text
schema_version: 1
kind: setup
data.config_path: string
data.steps_applied: array of setup step IDs
data.partial: boolean, present for --step
data.auth.agentkit: session_present, not_authenticated, or unknown
data.auth.kit_entitlement: not_checked or login_required
data.auth.runtimes: array of adapter, state, and optional action
data.previous_adapters: string, present when the run disabled an adapter
data.disabled_adapters: array of adapter IDs, present with previous_adapters
data.restore_command: string, present when the previous adapters can be restored
```

JSON-mode failures, including flag-parse errors (exit `2`), end stderr with the
shared [error envelope](../cli-conventions#json-output).

## Exit status

| Exit | Meaning | Safe next step |
| --- | --- | --- |
| `0` | Configuration was saved. | Review the reported path, then install a kit separately if needed. |
| `1` | Config read/write or adapter-config writing failed; a support report may be offered. | Inspect the error, any `~/.agentkit/support/setup-report-*.md` file, and current files before rerunning the same step. |
| `2` | Arguments, adapter selection, step ID, or required scripted input were invalid. | Correct the input; no validated setup result was produced. |
| `3` | The terminal wizard was cancelled. | Rerun when ready; cancellation does not save the form. |

## Effects, safety, and recovery

The command reads the existing AgentKit config and local AgentKit session. It
may start `claude auth status --json` and `codex login status` probes with short
timeouts to classify native login state. For `dsh` and `grok`, it resolves
`AGENTKIT_DSH_BIN` / `dsh` or `AGENTKIT_GROK_BIN` / `grok` but leaves
authentication state unknown and runtime-owned. It does not contact the AgentKit
registry, validate paid-kit entitlement, populate the kit cache, or install a kit.

Basic setup atomically creates or updates `~/.agentkit/config.yaml`, preserving
unmodelled YAML fields. Advanced steps can additionally write selected native
adapter configuration atomically. Setup does not create a recovery snapshot.

<Callout type="warning">
  The AgentKit config is saved before advanced adapter writes. If a later
  adapter write fails, exit `1` can leave the AgentKit config updated while the
  runtime config is unchanged. Inspect both files, correct the reported cause,
  and rerun the same `--step`; do not delete either runtime home.
</Callout>
