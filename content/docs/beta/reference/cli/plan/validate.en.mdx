Use `ak plan validate` to check the file format of one plan directory without
opening the local plan store.

## Usage

```bash
ak plan validate <path>
```

The command accepts exactly one directory path and has no command-specific
flags.

## What is validated

A valid directory must:

- contain a readable `plan.md`;
- provide a non-empty `title` in the simple leading front matter parsed by the
  command;
- contain at least one file named `phase-<number>-<slug>.md` that can be
  parsed;
- give each phase a unique whole-number ordinal. `phase-02-x.md` and
  `phase-2-y.md` both claim phase 2 and fail validation.

Validation names the files that share each number and flags numbers that are
out of range. Give each file an unused number. If phases must stay in order,
renumber the affected phase and the ones after it together.

Every `phase-*.md` file must match `phase-<number>-<slug>.md`. A file that does
not, such as `phase-02a-api.md`, `phase-02.md`, or `Phase-02-api.md`, is not
tracked as a phase, so plan status, check, and kanban skip it. Validation
reports it as an error; for a letter suffix, give the phase its own number and
renumber the phases after it.

Commands that sync the plan store refuse a plan with duplicate ordinals and
leave the store unchanged. Rename the files, rerun `ak plan validate`, then run
`ak plan reindex`.

Phase titles can come from front matter, the first H1, or the filename slug.
Checkboxes determine phase status when present. The check does not require all
tasks to be complete, validate plan-store synchronization, resolve a current
plan, or enforce arbitrary nested YAML fields.

This is a local, read-only command. It does not open/create/migrate the plan
store, spawn Git, use network/auth/providers, read stdin, or prompt. It has no
preview, apply, force, backup, or mutation recovery.

## Output contract

Valid human output starts with `[OK]`. Invalid human output starts with `[X]`
and lists validation messages. JSON uses `kind=plan.validate` with:

```text
data.valid: boolean
data.dir: the supplied path
data.errors: array of validation messages
```

<Callout type="info">
  An invalid plan still emits this normal report to stdout, including a JSON
  success-shaped envelope with `data.valid=false`, and then exits `3`. It does
  not emit a second JSON error envelope. Capture stdout even when the process
  status is non-zero.
</Callout>

## CI example

```bash
code=0
ak plan validate ./plans/my-plan --json >plan-validation.json || code=$?
# Read data.errors; code 3 means the plan content is invalid.
```

Preserve the command's status directly when you need to distinguish exit `3`
from other failures.

## Exit behavior and recovery

| Exit | Meaning | Safe next step |
| --- | --- | --- |
| `0` | The plan format is valid. | Continue with the workflow. |
| `3` | The directory or its plan content failed validation, including a missing `plan.md`. | Read stdout errors, correct the files, and rerun. |
| `2` | Arguments or flags were invalid. | Correct the invocation. |
| `1` | Rendering or another unclassified runtime failure occurred. | Inspect stderr and retry after fixing the environment. |
