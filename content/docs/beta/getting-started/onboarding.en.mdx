Onboarding is complete when your chosen coding assistant recognizes an Engineer
Kit Skill in a project you control.

## Before you start

You need:

- `ak` on your `PATH` — see [Installation](./installation).
- A supported coding runtime installed and signed in with its own provider.
- An AgentKit account with access to Engineer Kit.
- A test project where you can add runtime configuration.

<Callout type="info">
  AgentKit authentication grants access to licensed Kits. It does not sign
  Claude Code, Codex, Cursor, Grok, Pi, or Oh My Pi in to their providers, and
  runtime login does not grant AgentKit Kit access.
</Callout>

## Run onboarding

Change to the project where you want the Kit, then run the conductor:

```bash
cd /path/to/project
ak onboard
```

`ak onboard` checks three states in order and runs only the missing work:

| Step | Runs when | Result |
| --- | --- | --- |
| Setup | Basic AgentKit configuration is incomplete | Selects a runtime adapter, default Kit, and telemetry preference in `~/.agentkit/config.yaml` |
| Login | No renewable AgentKit CLI session exists | Signs in with email OTP or a user API key on a TTY |
| Kit install | No install receipt exists for the selected Kit, target, and scope | Installs the Kit through the normal Kit service in preserve-only mode |

Completed steps are reported as `skipped`, so you can rerun the command after a
partial or interrupted first use. `--yes` accepts prompts but never becomes
`--force`.

Choose the Kit, runtime, and release channel explicitly when you want a
repeatable result:

```bash
ak onboard --kit engineer --target codex --channel <channel>
```

Replace `<channel>` with the channel selected in the docs header. An explicit
`--channel stable` or `--channel beta` aligns both Kit downloads and binary
updates. With no channel flag, onboard preserves a configured channel, fills a
missing paired value, or uses `stable` when neither value exists.

The current project is the default install scope. From your home directory,
choose a user-wide install or cancel and change to a repository:

```bash
ak onboard --global --kit engineer --target codex --channel <channel>
```

`--project-dir` selects another project, but it cannot be the user home unless
you also pass `--global`. A project is recognized by `.git` or an existing
`.agentkit/ownership.json`; you do not need to run `ak init` before a
project-scoped Kit install.

## Use onboarding in automation

Non-interactive onboard cannot collect a new credential. Create the CLI session
first, then pass every choice the job depends on:

```bash
ak login --api-key ak_live_... --no-interactive
ak onboard \
  --no-interactive \
  --yes \
  --project-dir /path/to/project \
  --kit engineer \
  --target codex \
  --channel <channel>
```

Without a usable session, non-interactive onboard exits `2` instead of opening
a login prompt. Keep real API keys, OTPs, license keys, session files, and
provider credentials out of source control, screenshots, diagnostics, and
shared shell history.

## When to use the individual commands

You normally do not need to run setup, login, and Kit installation separately
during first use. Use their standalone forms when you need to change or recover
one layer without replaying the whole conductor:

| Command | Use it when |
| --- | --- |
| [`ak setup`](../reference/cli/setup) | Change adapters, the default Kit, telemetry, or advanced provider/model preferences after onboarding |
| [`ak login`](../reference/cli/login) | Switch AgentKit accounts, rotate a user API key, recover authentication, or create a session before automation |
| [`ak kit init`](../reference/cli/kit/init) | Install a specific Kit route after configuration and authentication are already known-good |
| [`ak init`](../reference/cli/init) | Ask AgentKit to adopt and track an existing project as a whole, including its ownership manifest and custom docs/plan paths |

These commands remain part of the CLI contract, but they are supporting paths,
not extra onboarding steps.

## Verify the result

Confirm the AgentKit account, Kit grant, and local installation health:

```bash
ak whoami
ak licenses
ak doctor --exit-on-fail
```

`ak whoami` exits `0` even when it reports an unauthenticated state. Scripts
must inspect the result rather than treating exit code zero as proof of login.
Continue only when `ak licenses` lists Engineer Kit and doctor reports no
blocking failure.

Restart the assistant or open a new session so it reloads the installed content,
then invoke one Skill:

invocation surface. Onboarding is complete when the assistant recognizes the
Skill, reads the request, and begins its workflow in the current project.

## Recovery and common failures

- **No AgentKit session:** rerun `ak onboard` on a TTY, or use an explicit
  [`ak login`](../reference/cli/login) method.
- **Engineer Kit is absent from `ak licenses`:** sign in with the account that
  owns the Kit. Reinstalling cannot create a missing grant.
- **Runtime missing or signed out:** install or sign in to that runtime with its
  provider account, then rerun onboard.
- **Skill not recognized:** confirm the install summary names the intended
  target, restart the assistant, and run `ak doctor --exit-on-fail` before
  reinstalling.
- **`channel_drift` warning:** align both channels with
  `ak onboard --channel stable` or `ak onboard --channel beta`.
- **Ownership conflict:** stop and inspect the reported destination. Do not add
  `--force` as the first response; onboard always uses preserve-only install.

For detailed Kit scope, target compatibility, refresh, uninstall, and recovery
behavior, continue with [Installing Kits](../guides/installing-kits). Otherwise,
go to the focused [Quickstart](./quickstart).
