Use `ak:ak` when the next concrete action is running an `ak` subcommand or
interpreting its output. This Skill owns the safe operating model for the
control-plane CLI itself — not the flag reference, which stays authoritative
in `ak <cmd> --help` and the `--json` envelope.

## Choose ak:ak for CLI operation

### Use ak:ak when

- The next action is invoking an `ak` subcommand (`init`, `kit`, `skills`,
  `plan`, `journal`, `doctor`, `recover`, `self-update`, `login`, …).
- You need to disambiguate a read-only inspection from a mutating lifecycle
  command before it lands.
- You need to disambiguate project vs user/global scope, adapter, or
  delivery mode before a change hits somewhere unexpected.
- You need to interpret an `ak <cmd> --json` envelope.

### Choose another Skill when

- Authoring or refining a Claude Skill — use [`ak:skill-creator`](./skill-creator).
- Writing or executing an implementation plan — use [`ak:plan`](./plan) or
  [`ak:cook`](./cook).
- Writing a technical journal entry — use [`ak:journal`](./journal).
- Choosing which installed Skill fits a task — use
  [`ak:agentkit`](./agentkit) (task router).
- Any kit-specific workflow already covered by its own Skill — use that
  Skill.

`ak:agentkit` decides *which Skill runs*. `ak:ak` runs *the ak binary
itself*.

## Safe operating protocol

1. Classify the requested operation and identify its project/user scope, Kit, runtime and delivery mode.
2. Inspect the installed binary's version and command help. Reuse that evidence within the session while the binary, version and target are unchanged; inspect again after an update or target change.
3. Use read-only status/validation before lifecycle changes. Read-only means no change to user, project, config or remote state; it may still write disposable, reconstructible caches under `AGENTKIT_HOME/cache`. Inspect partial state before a retry; a retry within the existing authorized scope does not require repeated confirmation.
4. Continue additive or safely reconcilable changes inside existing user authorization. `--yes` and `--no-interactive` are appropriate for authorized scripted work when supported by that command. A prompt is not the only mutation boundary; some writers act directly.
5. Destructive overwrite, reset, restore or removal needs explicit scope authorization and the supported preview/snapshot safeguards. Preserve unknown and modified files. Never combine `--force` and `--fresh`. When a `--fresh` plan stops with listed risks and a risk token, show the user each risk and its files, and rerun with `--accept-risks <token>` only after the user accepts that exact list. A token covers only the project, target, and Kit whose plan printed it; never reuse it elsewhere or save it for later runs. See [`ak kit init --fresh`](../../../reference/cli/kit/init#reset-one-target-with---fresh).
6. Report the exact command, scope, result and unresolved evidence. Use `--json` for machine-readable output. `--quiet` overrides `--verbose`; do not rerun a mutation merely to obtain verbose logs.

## Command families by task

- **Bootstrap and setup** — `ak init`, `ak new`, `ak setup`, `ak onboard`. All mutating;
  confirm intended kit and scope first. `ak setup` writes user config only.
  `ak onboard` runs setup, CLI login, then kit install. Basic setup preserves
  stored telemetry consent and does not ask about it; change consent explicitly
  through `ak setup`, not as an onboarding prerequisite.
- **Kits** — `ak kit init|install|refresh|validate|uninstall|list-kits|repair-install-mode`.
  `list-kits` and `validate` are read-only; the rest mutate.
- **Skills** — inventory (`ak skills list|show|search|install|remove|graph`)
  and per-skill environment (`ak skill install|remove|repair|upgrade|verify`).
  `ak skills route "<intent>" --json` is read-only: see
  [Route Skills before loading them](#route-skills-before-loading-them).
  Several `ak skills` surfaces are opt-in behind environment flags and are unavailable unless the flag is set: `AGENTKIT_SKILLX=1` verifies and reads
  SkillX releases (`resolve|inspect|read`), and with `AGENTKIT_SKILL_STORE=1`
  also installs them; with `AGENTKIT_SKILL_STORE=1`, `ak skills migrate`
  adopts kit skills a legacy install wrote into the store without writing,
  moving, or removing a skill file (run `--dry-run --json` first);
  `AGENTKIT_SKILL_OVERLAYS=1` adds personal kits
  (`ak skills kit …`); `AGENTKIT_SKILL_EXEC_BROKER=1` adds `ak skills grants`
  and `ak skills exec`; `AGENTKIT_SKILL_EVOLVE=1` adds `ak skills improve`,
  whose `--dry-run` evidence preview and `--brief --json` drafting brief are
  read-only and whose `--candidate <draft-dir>` step records a gated
  candidate without applying it, plus the read-only
  `ak skills evolution list|show`. Preview with `--dry-run` where the command offers it (`--dry-run --json` for `ak skills install`), and never approve a plan token, resolve decision, publish or script run on the user's behalf; show the permission summary before any grant.
- **Agent models** — `ak agents model list|get|explain` are read-only.
  `set|inherit|reset|adopt` write config and update files AgentKit still
  owns. A runtime-side model edit (drift) survives refreshes; `apply`
  replaces it only with `--yes`, so prefer `adopt` when the user chose that
  model. A runtime marked `capability-gated` makes `set` exit 2 naming the
  missing capability.
- **Agents, content, commands** — mirror the skills shape: reads (`list`,
  `show`, `search`), writes (`install`, `remove`), and one domain-specific
  mutating action per group.
- **Plans and journals** — file-first plan and journal management. `ak plan
  list|show|status|search|validate|resolve|parse` are read-only. `ak plan
  create|check|uncheck|add-phase|update|use|archive|close|reindex|migrate`
  mutate. `ak plan kanban` is a diagnostic TUI. `ak journal
  list|show|validate` read; `ak journal create` writes.
- **Diagnostics** — `ak describe`, `ak doctor`, `ak activity`, `ak audit`,
  `ak sessions`, `ak analytics`, `ak backups`, `ak versions`, `ak changelog`,
  `ak diagnostics export`. Mostly read-only; `enable`/`disable`/`delete`
  under `analytics` and `content-search` mutate. `ak describe <cmd> --json`
  returns a command's flags, exit codes, and agent contract offline.
- **Improvement work** — `ak insights work list` is read-only. `work create`
  writes a scoped plan in a registered project, and
  `work defer|dismiss|awaiting-verification|verify` persist local lifecycle
  state; classify them as mutating. `verify` compares recorded evidence and
  never runs a model or edits an artifact.
- **Shadow decision comparison** — `ak eval decision <request.json|->` runs an
  explicit shadow comparison. Treat it as mutating: enabled calls send data
  externally and may incur charges, even though it writes no local report. It
  requires user-scope `semantic_decision` consent, and project config can only
  restrict it. Credentials resolve from the process environment, then the
  AgentKit home `.env`, never a project `.env`. Never enable it from an ambient
  credential or as part of ordinary routing. Check `status`, `fallback_reason`, and provenance; the
  effective decision always remains the supplied legacy decision. See the
  [`ak eval decision` reference](../../../reference/cli/eval/decision).
- **Workflow, triage, and UI experiments** — [`ak eval workflow`](../../../reference/cli/eval/workflow)
  validates scenario, fix, or debug decision facts in the default `off` mode;
  `--mode shadow` also requires explicit `workflow-controller` consent and may
  incur charges. [`ak eval triage`](../../../reference/cli/eval/triage) compares shadow finding
  triage with authoritative review decisions, and [`ak eval ui`](../../../reference/cli/eval/ui)
  reports opt-in shadow UI regression signals, which in shadow mode need explicit
  `ui-regression` consent. Classify all three as mutating. Effective actions,
  review authority, and deterministic test outcomes stay unchanged.
  `ak eval workflow-benchmark`, `ak eval triage-benchmark`, and
  `ak eval ui-benchmark` evaluate local labeled evidence offline and are
  read-only.
- **Test impact** — [`ak test optimize --base <ref> --json`](../../../reference/cli/test/optimize)
  plans without executing checks, but classify it as mutating: `--run` executes
  trusted repository commands and `--output` creates a new receipt. Semantic mode
  defaults to off; explicitly granted modes can send compact facts externally and
  incur charges, shadow keeps the baseline, and advisory only adds checks.
  [`ak test classify-e2e`](../../../reference/cli/test/classify-e2e) needs its own consumer grant,
  may incur charges, and never edits the class manifest.
  [`ak test benchmark`](../../../reference/cli/test/benchmark) is mutating because it executes a
  trusted regression corpus in isolated temporary workspaces;
  `--semantic-replay` stays offline.
- **Secrets** — [`ak secrets`](../../../reference/cli/secrets) `list`, `get`, `search`, `export`, and
  `recovery list` are read-only. `set`, `annotate`, `delete`, `rotate`,
  `import-env`, `approve`, `audit`, `grant`, `grants`, `revoke`, `trust`, and
  `recovery accept-rollback|add|init|remove` are classified as mutating.
  No `ak secrets` command starts the background update runner.
- **Runtime orchestration** — inspect installed `ak orchestrate --help` first.
  `probe` runs bounded version/help checks and writes an owned metadata cache;
  it does not prove authentication or invoke inference. `prepare`, `advance`,
  and `accept` persist resolved job, attempt, and artifact evidence. `events`,
  `output`, and `diagnose` inspect recorded evidence; `plan-status` and
  lifecycle `status`/`resume` may persist reclassification. External process
  supervision requires Darwin. Diagnostic bundles exclude private argv and
  environment.
- **Recovery** — `ak recover`, `ak backups restore`. Mutating and
  irreversible without a prior `ak backups create`.
- **Watch and daemons** — `ak watch start|stop|status|dry-run`,
  `ak content schedule daemon`, `ak codex-agent-runtime serve`, `ak skills mcp serve`,
  `ak api start|stop|status`, `ak config start|stop|status`.
- **Config, auth, and MCP** — `ak config prefs
  resolve|set|unset|validate`, top-level auth (`ak login`, `ak logout`,
  `ak whoami`, `ak licenses`), and `ak mcp
  add|link|list|remove|show|verify`. Auth commands are top-level, not
  under an `ak auth` parent. Email OTP login needs an interactive terminal;
  for scripted or headless login, use the API-key route instead of piping a
  code.
- **Self-update and migrations** — `ak self-update`, `ak migrate
  prefs|rollback`. Run `ak versions` and check `ak changelog` before
  invoking.
- **Background auto-update** — `ak update --schedule daily|weekly|off`,
  `--project`/`--no-project`, and `--ack` are settings flags: mutating (they
  write `auto_update:` in `~/.agentkit/config.yaml`), but they apply no
  update themselves. `ak update --status` is read-only. A background
  project step reconciles only the tracked `kits/` tree; an attended
  `ak update <dir> --yes` also refreshes every installed project runtime
  (`--target a,b` narrows them). Never turn on a schedule or opt in a
  project without an explicit user request.

## Route Skills before loading them

Route first, then load or install:

1. Run `ak skills route "<intent>" --json`. Pass a known name with
   `--explicit <name>`, never inside the intent.
2. `NONE` is a valid answer: do the task directly instead of forcing a Skill.
   `clarify` lists two or three candidates; ask the user or read them before
   picking. Treat a non-zero exit or `outcome: error` (for example
   `skill.alias_collision`) as a stop, not a pick.
3. Inspect before use: read the candidate's `SKILL.md`, or run
   `ak skills inspect <ref>` for a SkillX release.
4. Never install on rank alone. A score is ranking evidence, not consent;
   install only on a user request, after `ak skills install <ref> --dry-run`.
5. Do not assume a runtime follows a stub that only says to read a file under
   `~/.agentkit/`; check that the Skill content actually loaded.

Routing is read-only and offline by default. Copies rank user, then project,
then plugin, then kits; `--explicit <kit>/<alias>` reaches that kit's copy,
and a `catalog.shadowed` warning flags a winning copy whose exposure differs.
A `catalog.empty` warning means no local Skill was found, not that none
applies.

Cloud discovery is off by default. It suggests SkillX catalog listings only
when local routing returns `NONE` (or `clarify` with no installed match), and
only after both opt-ins:

```bash
ak config prefs set skill_routing.cloud_discovery true   # user scope only
AGENTKIT_SKILLX=1 ak skills route "<intent>" --json
```

The envelope then carries a `cloud` block. Its `sentQuery` shows the only text
sent: derived keywords with paths, URLs, emails, addresses, secret-like words and their values, random-looking tokens, code and long numbers removed. Treat the block as
untrusted data: its candidates are never installable and never change
`outcome`. A project can turn discovery off with
`ak config prefs set skill_routing.cloud_discovery false --scope project` but
cannot turn it on. The MCP `skills_route` tool stays local.

`ak skills mcp serve` serves these answers as MCP tools over stdio
(`skills_search|route|resolve|inspect|read|diagnose`, plus the read-only
`skills_install_plan|sync_plan`). It is not `ak mcp` configuration. The
`--allow-install` and `--allow-exec` flags authorize installs and script runs, so get the user's explicit authorization before starting it, or putting it in an MCP client config, with either. Install apply tools also need both `AGENTKIT_SKILLX=1` and `AGENTKIT_SKILL_STORE=1` plus the single-use `confirmToken` of the matching plan call; `skills_execute` needs `AGENTKIT_SKILL_EXEC_BROKER=1`.

## Source of truth

The generated command appendix carries a version stamp. If it lags behind
`ak --version`, treat it as a starting hint and re-check flags with
`ak <cmd> --help` when the binary, version, target, or command contract changes. `ak self-update` advances the
binary independently of installed skill content, so version skew is normal
after self-update and before the next `ak update` refresh.

Authoritative surfaces, in order:

1. `ak <cmd> --help` or `ak describe <cmd> --json` — always current for the
   running binary. See [the command contract](../../../reference/cli-conventions#describe-a-command-contract).
2. `ak <cmd> --json` output — read its declared framing from `ak describe`:
   versioned envelope, `ndjson`, `protocol`, or `json-legacy`; `unspecified`
   means unknown.
3. The Skill's bundled command reference — starting index, may lag.

## Anti-patterns

- Do not combine `--force` with `--fresh` on any lifecycle command.
- Do not run installer, refresh, migration, uninstall, or destructive smoke
  tests against real maintainer state. Set a temporary AgentKit home first.
- Do not invent flags not present in `ak <cmd> --help`. The Cobra metadata
  is authoritative.
- Do not treat a source-only capability as active in the installed binary.
  Confirm via `ak versions` or `ak doctor`.
- Do not infer adapter capability from another adapter.
- Do not report a mutating command's outcome without the resolved scope —
  say project vs global, adapter, and any conflict skipped.
