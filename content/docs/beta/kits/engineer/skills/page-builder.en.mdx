title: Build an agent-operated page builder with ak:page-builder
description: Integrate or extend a project page builder with existing components, drafts, previews, publishing, and a project operator Skill.
---

Use `ak:page-builder` to integrate a dynamic page builder into the current
project using that project's stack, components, and design system. Agents are
the primary operators. Humans can still customize pages through an accessible,
responsive, touch-friendly editor. The Skill delivers working project code,
verified interfaces, and a project-specific operator Skill created through
installed `ak:skill-creator`.

`setup`, `update`, and `operate` are Skill arguments, not `ak` CLI subcommands.

## Choose ak:page-builder for a reusable composition system

### Use ak:page-builder when

- You need a reusable page composition system, component registration, or
  draft, preview, publishing, and agent operation on an existing builder.
- You are extending a builder with new blocks, bindings, layouts, or interface
  contracts.
- Routine page changes should go through the project's operator Skill, and that
  Skill is not available yet, so this Skill's operate path is required.

### Choose another workflow when

- The request is one-off page design. Use the matching design or frontend Skill.
- You only need a generic CLI or MCP wrapper around an existing API. Use
  [`ak:mcp-builder`](./mcp-builder) or [`ak:agentize`](./agentize).
- You need an implementation plan before touching the builder. Use
  [`ak:plan`](./plan), then return here.
- You need independent verification of the delivered builder. Use
  [`ak:test`](./test).

## Prepare the project and authority boundary

Before you start:

- Complete [Onboarding](../../../getting-started/onboarding), and confirm
  Engineer Kit is installed for the runtime and scope you are using.
- Open the project whose components and design system the builder must reuse.
- State whether drafts, shared previews, publication, MCP, or HTTP surfaces are
  in scope.
- Keep publication, production writes, and credentialed provider calls behind
  explicit approval.

| Runtime | Invocation | Availability boundary |
| --- | --- | --- |
| Claude Code | `/ak:page-builder ...` | Runs as an installed Engineer Skill under native or explicit plugin delivery. |
| Cursor | `/ak:page-builder ...` | Uses the user-verified slash spelling; broader tool parity is not established. |
| Codex | `$ak:page-builder ...` | Uses native Codex discovery; this does not imply parity for every Engineer runtime component. |

Infer `setup`, `update`, or `operate` from the request and existing project;
explicit arguments win. Reuse accepted outcomes, constraints, non-goals, and
acceptance criteria. Inspect the repository before asking about a choice the
source can answer.

<Callout type="info" title="Default new-builder scope">
  A new builder includes component discovery and registration, configurable
  props and bindings, drag-and-drop with adaptive small, medium, and large
  widget sizes, drafts, shared previews, publication, and agent interfaces.
  Do not invent a separate product surface that the project stack does not
  already support.
</Callout>

## Verify the result

- The builder uses existing project components rather than a parallel design
  system.
- Preview and publication paths are explicit and gated.
- A project operator Skill exists or the operate path is documented as the
  temporary fallback.
- Tests or interface checks cover the accepted contracts.

Continue with [`ak:test`](./test) for independent verification and
[`ak:skill-creator`](./skill-creator) if the operator Skill still needs to be
authored.
