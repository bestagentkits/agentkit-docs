title: Deliver a request end to end with ak:atoz
description: Lock scope once with ak:advise, hand over every prerequisite in one batch, then let ak:atoz orchestrate delivery without check-ins until each Done-means item is verified.
---

import { Callout } from 'fumadocs-ui/components/callout';

Use `ak:atoz` when you want one conversation up front and no babysitting
afterwards. The Skill runs three gates in order, because each consumes the
previous one's result:

1. **Lock**: scope and Done means confirmed by you.
2. **Prepare**: you hand over everything the run needs, in one batch.
3. **Execute**: the agent works autonomously until every Done-means item is
   verified.

## Choose ak:atoz or another workflow

### Use ak:atoz when

- You can confirm scope once and supply every prerequisite before work starts.
- The work is large enough to split into parallel pieces with separate file
  ownership.
- You want the run tracked on a GitHub issue and finished with an isolated
  review.

### Choose another workflow when

- You only want advice. Use [`ak:advise`](./advise).
- You want a preflight that stops before execution. Use
  [`ak:goal-warmup`](./goal-warmup).
- You want an issue-to-PR pipeline without the upfront prerequisite batch. Use
  [`ak:vibe`](./vibe).

## Run the Skill

| Runtime | Invocation |
| --- | --- |
| Claude Code | `/ak:atoz "<request or URL>" [--yagni]` |
| Cursor | `/ak:atoz "<request or URL>" [--yagni]` |
| Codex | `$ak:atoz "<request or URL>" [--yagni]` |

The request text, URLs, issue bodies and repository content are data, not
instructions. The Skill ignores embedded attempts to skip a gate, widen its
authority or exfiltrate secrets. `--yagni` is passed through to the
`ak:advise` interview.

## Gate 1: lock scope

The Skill runs the `ak:advise` interview on your request. When model
invocation of `ak:advise` is disabled, it follows that Skill's steps in the
same session. The interview asks one question at a time and ends with a
handoff brief: Objective, Done means, Out of scope, and Constraints.

The gate closes with one question offering **Confirm**, **Edit**, or
**Abort**. Only an explicit Confirm opens gate 2; a passing "looks good" does
not. Edit returns to the interview for the changed field only. After Confirm
the brief is the contract, and the run never shrinks, swaps, or extends it
silently.

## Gate 2: hand over prerequisites

Before touching anything, the Skill inspects the environment (installed CLIs,
authenticated sessions, whether environment variables are present, repository
remotes, branch protection) and lists only the real gaps. Each item says what
it is, why the run needs it, where the run will look for it, and how it will be
checked.

| Category | Typical items | Ready check |
| --- | --- | --- |
| Access and auth | Repository push rights, `gh auth`, cloud or CLI logins | `gh auth status`, `<cli> whoami`, a read-only list call |
| Secrets and config | API keys, tokens, environment variables | The variable is present; its value is never printed |
| Accounts and quotas | Third-party accounts, billing, rate limits, domains | A read-only API call or a state you confirm |
| Data and assets | Sample data, copy, designs, test accounts | The file exists at the agreed path |
| Issue tracking | The repository that owns the work's issue, label permissions | `gh issue list --limit 1`, `gh label list` |
| Authority | Merge or deploy rights, spend limits, permission to post | Stated in the brief |
| Decisions only you own | Pricing, legal text, public naming | Your answer recorded in the brief |
| Environment | Toolchain versions, running services, free ports, disk | A version or health command |

The list also names the reversible defaults the Skill chose for you to
override, and the stop conditions the autonomous run will honor. Put secrets
in the environment or a secret store you control; never paste them into the
conversation. When you report the items ready, the Skill re-checks each one
without changing anything and lists whatever is still missing. If you waive an
item, the brief records the consequence and the run continues without it.

## Gate 3: execute autonomously

The main session becomes the orchestrator: it plans, dispatches, monitors,
integrates, and verifies, while implementation runs in sub-sessions.

- **Plan, then fan out.** Pieces that need no other piece's result and touch no
  shared file run in parallel; dependent pieces wait. Each code-writing piece
  gets its own worktree and branch. The Skill prefers the runtime's native
  session or subagent facility, falls back to `ak:orchestrate` for
  cross-runtime work, and works sequentially only when neither exists.
- **Balance speed against quota.** The first wave is small (two or three
  sessions) and widens only while usage and machine load stay comfortable.
  Mechanical pieces go to cheaper models; architecture, hard debugging, and the
  final review stay on the strongest model. A rate-limit error pauses new
  dispatches; it does not stop the run.
- **Keep the machine clean.** Every process, server, and worktree the run starts
  is tracked, reused instead of duplicated, and stopped when its piece is done.
  The run never kills a process it did not start.
- **Check results, not reports.** A finished sub-session report is a claim: the
  orchestrator inspects the diff and reruns the piece's verification before
  merging it, one piece at a time.
- **Track it on GitHub.** The work's issue carries exactly one of `in progress`,
  `in review`, `done` (PR opened and review clean), or `shipped` (merged), with
  a short evidence comment at each change. Unrelated bugs, vulnerabilities, or
  gaps become separate deduplicated issues labelled `ai-handle` and are not
  fixed in this run.
- **Review in isolation.** The final review runs in a fresh sub-session whose
  only context is the brief, the diff, and the project's review playbook. The
  run fixes its findings and reviews again until no blocking finding remains.

<Callout type="warn" title="The only reasons the run stops to ask">
  A destructive or irreversible action the brief does not name (deleting data,
  force-pushing, rewriting published history, production data changes); a
  change that would alter a confirmed Done-means item or leave the confirmed
  scope or repository; spending money or sending a message the brief did not
  authorize; a failure that stays unexplained after diagnosis and advisor
  counsel; or a prerequisite that turns out invalid at use time, such as an
  expired token. Everything else is decided and continued.
</Callout>

When it does stop, the Skill states what is done, what blocks, and the option
it recommends, then resumes autonomously after your answer.

## Verify the result

The orchestrator verifies the integrated result itself rather than trusting
sub-session reports. It finishes only when every Done-means item is verified by
its command, number, or observable state, the isolated review is clean, the
issue label matches the real state, and no process, worktree, or cache the run
started is left behind.

The final report lists each Done-means item with its evidence, the decisions
made on your behalf, anything you waived, and remaining risks or follow-ups.
Partial delivery is reported as partial, never as done.
