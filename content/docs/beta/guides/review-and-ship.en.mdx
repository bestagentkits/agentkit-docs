Implementation is not done until review and shipping hygiene pass. This guide
covers the tail of delivery after cook/test (or after a focused fix).

<Callout type="info">
  Ship flags such as `--dry-run` and `--skip-tests` are documented on the
  [Engineer kit cheatsheet](../kits/engineer). Skipping gates is explicit debt.
</Callout>

## When to use

- Feature branch is green locally and ready for a PR.
- You want a structured review before human reviewers see the diff.
- You need a consistent path to `beta` or `official` branches.

## Workflow

<Steps>
<Step>

### Review the diff

```text
/ak:code-review
# or
/ak:review-pr
```

Ask for concrete findings (correctness, regressions, secrets, public contract
churn). Fix blocking issues before commit split.

</Step>
<Step>

### Commit cleanly

```text
/ak:git cm
```

Prefer conventional, single-line subjects. Let the skill split mixed concerns
and scan for secrets. Avoid bundling unrelated config with feature code.

</Step>
<Step>

### Ship the branch

```text
/ak:ship beta
# or
/ak:ship official
```

Ship merges the pipeline (tests, review, push, PR) toward the branch you name.
Use `--dry-run` first on unfamiliar repos. Prefer not to combine
`--skip-tests` with `--skip-review`.

</Step>
</Steps>

## Sample prompts

```text
/ak:code-review Focus on auth session edge cases
/ak:git cm
/ak:ship beta --dry-run
/ak:ship beta
```

## Pitfalls

- **Review theater** — reading the skill output without fixing findings.
- **Secret leakage** — never commit tokens; re-run the git security scan after
  amend mistakes.
- **Wrong track** — `official` vs `beta` is a product choice; match your release
  process.
