This is the default Engineer kit path for multi-step delivery: bound the work,
plan it, implement it, prove it, then open a PR. Worked example: **add a feature**
(not a one-line typo fix).

<Callout type="info">
  Claude Code uses slash skills (`/ak:plan`). Codex uses the dollar form
  (`$ak:plan`). Same skill name and flags either way. See the
  [Engineer kit cheatsheet](../kits/engineer) for every flag.
</Callout>

## When to use this workflow

- You have a product or maintainer change that needs more than a single edit.
- Requirements are fuzzy, or several approaches are still plausible.
- You want a durable plan before code, and a verified PR at the end.

Skip the full loop for direct Q&A or tiny, fully specified fixes — or jump
straight to `/ak:fix` when the work is a diagnosed bug (see
[Debug and fix](./debug-and-fix)).

## Workflow

<Steps>
<Step>

### Bound the outcome

```text
/ak:brainstorm Add export to CSV on the orders table
```

Capture **outcome**, **constraints**, **non-goals**, and **acceptance criteria**
before design debates. Reuse an accepted plan or design if you already have one;
only fill material gaps.

</Step>
<Step>

### Plan the work

```text
/ak:plan Add CSV export for orders — columns, auth, tests, empty states
```

Useful flags when the skill’s `SKILL.md` documents them:

- `--fast` — thinner research path
- `--html` — self-contained plan artifact
- `--tdd` — tests-first structure per phase

Read every generated phase stub before filling it. Prefer CLI plan scaffolding
when `ak` is available.

</Step>
<Step>

### Implement against the plan

```text
/ak:cook path/to/plan.md
# or
/ak:cook Add CSV export for orders --fast
```

Cook expects a concrete scope (plan path or clear task). Default mode is
interactive; `--auto` only when you accept auto-approval. `--no-test` weakens
the test gate — call that trade-off out explicitly.

</Step>
<Step>

### Prove the change

```text
/ak:test
```

Run the suite that covers the new surface and any shared contracts you touched.
Treat failing tests as a stop, not a ship note.

</Step>
<Step>

### Commit and open the PR

```text
/ak:git cm
/ak:ship beta
```

`/ak:git` splits conventional commits and scans for secrets. `/ak:ship` runs the
branch → test → review → push → PR pipeline (`beta` or `official`). Use
`--dry-run` on ship when you only want the plan of action.

Optional: `/ak:journal` after a hard session so the next run inherits context.

</Step>
</Steps>

## Sample prompts

```text
/ak:brainstorm We need rate limits on the public API — what is in scope for v1?
/ak:plan Rate-limit public API with Redis, 100 req/min, document headers
/ak:cook plans/…/plan.md --tdd
/ak:test
/ak:ship beta --skip-journal
```

## Pitfalls

- **Coding before the contract** — vague “make it better” prompts burn tokens;
  brainstorm first when outcome or acceptance is unclear.
- **Skipping scout evidence** — cook still needs current codebase context; don’t
  invent paths.
- **Shipping untested** — `--skip-tests` / `--no-test` are escape hatches, not
  defaults.
- **Mixing release tracks** — `ship beta` and `ship official` target different
  branches; pick one deliberately.
