The `ak` CLI and installed kits have separate release lifecycles. Updating the
CLI does not replace kit content, and refreshing a kit does not replace the CLI.
Check and update each layer deliberately.

## Choose a channel

AgentKit publishes `stable` and `beta` release channels:

- Choose `stable` for the regular release line.
- Choose `beta` when you intend to test prerelease behavior and can review
  compatibility changes.

Kit commands default to `stable`; `beta` requires an explicit opt-in. The CLI
self-updater uses `--channel`, then the saved `updates.channel`, then the channel
of the running release binary, then `stable`, so pass `--channel stable` or
`--channel beta` when the choice matters. Keep the CLI and kits on the same
intended channel.

The examples below use `stable`. Replace it with `beta` as a complete decision,
not as a one-off troubleshooting step.

## Use the unified updater when appropriate

In an interactive terminal, bare `ak update` walks through the signed CLI
update, global kits, then project kits. Every step defaults to No:

```bash
ak update
ak update --yes
```

`--yes` accepts the offered steps, but the signed CLI update or minimum-version
check remains a hard gate before any Kit mutation. Use the scoped commands below
when you want to update only one layer. A CLI hard-gate failure, partial Kit
failure, or interruption after mutation exits `1`; an invalid target, scope, or
source exits `2`.

On Windows, that CLI gate applies the replacement in place under an exclusive update lock, validates the running binary preimage, then re-executes the original `ak update` command so Kit refresh continues on the first invocation. Standalone `ak self-update` still uses the staged detached helper. Paired Desktop apply stages the matching CLI and Desktop artifacts, then a trusted helper commits the swap after the parent process releases the executables.

The wizard projects one `--target` selection onto each step. For example, `pi`
remains eligible for the project step but is omitted from the global Kit step;
if no selected target applies globally, the wizard skips that step and continues.
An explicit target that does not apply to the selected scope and source is
rejected before discovery or mutation.

## Review the CLI release

Read the verified changelog, check availability, or fully verify an update
without replacing the binary:

```bash
ak self-update --changelog --channel stable
ak self-update --check --channel stable
ak self-update --dry-run --channel stable
```

`--changelog` is a read-only mode and cannot be combined with update flags.
`--dry-run` downloads and verifies the required artifact in temporary staging,
then leaves the installed binary unchanged.

## Update the CLI

Apply after the check succeeds:

```bash
ak self-update --channel stable --yes
ak --version
```

The updater verifies release metadata and artifact bytes before replacement. If
replacement fails, it restores the previous binary as part of the transaction.
There is no user-facing `ak backups restore` step for a CLI binary update.

### Package-manager installs

If the running `ak` executable belongs to Homebrew or Scoop, `ak self-update`
does not replace it. Run the manager-native command it reports:

```bash
brew upgrade ak
scoop update ak
```

Detection is based on the resolved running executable and the package manager's
receipt, not merely on whether the manager is installed somewhere on the
machine.

## Preview a project kit update

`ak update` previews by default unless you confirm with `--yes`. Pin the project,
kit, and channel so the plan is unambiguous:

```bash
ak update . --kits engineer --channel stable --show-diff
ak update . --kits engineer --channel stable --show-diff --dry-run
```

The preview does not write files or create a snapshot. It classifies incoming
files and shows which user-modified files would be skipped. Without `--yes`, an
implicit scripted preview exits `3`; explicit `--dry-run` performs the same
non-mutating preview and exits `0`, which is more convenient in CI. Apply the
reviewed plan with:

```bash
ak update . --kits engineer --channel stable --yes
```

After the tracked `kits/` tree, an applied project update also refreshes every
installed runtime of each project kit (`.claude`, `.codex`, and adapter roots),
one pass per kit and runtime. A project with only `ak kit init` runtime installs
refreshes those. Preview and `--dry-run` list the planned runtime refreshes
without writing. A failed pass does not stop the others, and the command exits
`1` at the end. Narrow the runtimes with `--target`:

```bash
ak update . --target claude-code,codex --yes
```

A requested runtime with no project install is reported under
`skipped_targets`. A project directory that resolves to the user-level install,
such as the home directory, skips its runtime refresh and points to
`ak update --global`. Project `--force` does not archive legacy ClaudeKit Codex
skills; that stays `ak update --global --force` or `ak migrate --from ck`. See
[Project runtime refresh](../reference/cli/update#project-runtime-refresh).

By default, an applied project update snapshots only the exact files it writes
or prunes — a restorable bundle, whose result includes the restore command.
`--force`, `--backup`, or `backups.enabled: true` in `~/.agentkit/config.yaml`
captures the whole project instead; `--no-backup` skips the snapshot
entirely, including the one `--force` takes. By default, user-modified files
are preserved. Use `--force` only after reviewing the exact diff and deciding
that the snapshot is sufficient recovery; it is not a routine refresh flag.

<Callout type="warn" title="--no-backup skips recovery snapshots">
  Preview and `--dry-run` still write nothing. Applied `ak update` snapshots
  by default: the exact changed files unless `--force`, `--backup`, or
  `backups.enabled: true` is set, in which case it captures the whole
  project. Passing `--no-backup` is an explicit opt-out: the command warns on
  stderr, and `--force --no-backup` adds an escalated warning. Structured
  results report `backup_skipped` so a missing `snapshot_id` is not enough to
  tell an intentional skip from a no-op. A Desktop plan apply that keeps user
  content takes the same exact-file capture, widening to the whole project
  only when user content is overwritten or `backups.enabled` is set; it does
  not accept `--no-backup`. `--backup` and `--no-backup` are mutually
  exclusive, and `--backup` does not widen global kit refresh snapshots. The
  same `--no-backup` flag also exists on [`ak init`](../reference/cli/init)
  (opt-in via `--backup` or `backups.enabled`, off by default),
  [`ak kit init`](../reference/cli/kit/init),
  [`ak kit install`](../reference/cli/kit/install), and
  [`ak kit refresh`](../reference/cli/kit/refresh) — review the data-loss
  warning before using it.
</Callout>

For when each lifecycle command snapshots automatically and how `backups.scope`
limits a `~/.claude/` capture, see [`ak backups`](../reference/cli/backups).

## Background auto-update (opt-in)

`ak update --schedule daily|weekly` enables a detached background update that
starts on the first ordinary `ak` command after the interval, refreshing the
CLI and global kits plus any project opted in with `--project <dir>`
(registered via `ak projects add`) whose git tree is clean and has no live
agent session. A background project update refreshes only the tracked `kits/`
tree; it never refreshes runtime installs and records a notice to run
`ak update <dir> --yes` instead:

```bash
ak update --schedule daily --project .
ak update --status --json
ak update --schedule off
```

The settings flags (`--schedule`, `--project`, `--no-project`, `--status`,
`--ack`) only change `auto_update:` in `~/.agentkit/config.yaml` or read state;
they never apply an update themselves and cannot combine with an update flag
or a project-dir argument. Background updates never start with
`AK_NO_AUTO_UPDATE=1` or `CI` set, for `--json` invocations, or for
lifecycle/interactive commands such as `update`, `init`, or `kit`. A Kit hook
(`session-heartbeat.cjs`) marks a project as having a live session so the
updater skips it; an unacknowledged result prints once at the next
`SessionStart` and can be acknowledged with `ak update --status --ack --json`.
See the [`ak update` reference](../reference/cli/update) and the
`auto_update` [`ak doctor`](../reference/cli/doctor) check for details.

The background run uses the release channel from `updates.channel`; the
`auto_update:` key holds only the schedule and opted-in projects. A project that
has uncommitted changes or a live agent session is not updated; it stays pending
and is retried on the next due run. A project that is not a git repository is
skipped. Global Kits update whether or not agent
sessions are live, just as an interactive `ak update --global` would.

Each background result is shown once: as a one-line summary on the stderr of the
next interactive `ak` command, or through the session-start notice, whichever
comes first. `ak update --status` keeps showing it, and the `ak doctor`
**Auto-update** check reports the schedule, the last result, a stuck or
overdue run, and opted-in projects that can no longer be updated.

Session detection depends on which events a runtime delivers to the
`session-heartbeat.cjs` Hook:

- Codex has no `SessionEnd` event, so its session markers expire only after
  their time-to-live.
- Pi runs the Hook on session start, prompt submit, and stop, but defers
  `SessionEnd`; its markers also expire by time-to-live.

The clean git tree check still protects uncommitted work when a session goes
undetected.

On Windows, the background run must leave the terminal's job object. When that
job forbids breakaway, AgentKit does not start the run inside the job; it records
the run as `deferred (spawn_in_job)` and retries later.

## Preview global kit updates

Global update discovers AgentKit-owned user-scope installs. Preview all of them,
or filter by kit and runtime:

```bash
ak update --global --channel stable
ak update --global --kits engineer --target codex --channel stable
ak update --global --kits engineer --local --kits-dir ./kits --target grok
```

Apply only after the preview identifies the expected installs:

```bash
ak update --global --kits engineer --target codex --channel stable --yes
ak update --global --kits engineer --local --kits-dir ./kits --target grok --yes
```

Global update is preserve-only for user-modified files. Target validity depends
on both scope and source: remote project updates accept any of
`claude-code`, `codex`, `cursor`, `dsh`, `grok`, `omp`, or `pi`; remote global
updates accept `claude-code`, `codex`, `cursor`, `dsh`, `grok`, or `omp`; local
global updates accept the same set. Use `--target` or its `--runtime` alias, but
pass only one flag name. An explicit target that does not apply to the selected
scope and source is rejected before discovery or mutation.

A selected runtime that is not installed globally is reported as skipped rather
than created. In an unfiltered remote `--global` run, an existing local-only
install remains visible as a skipped result with reason `source_inapplicable`;
it is not refreshed from another source implicitly. Follow its `next` guidance
and run `ak update --global --local --kits-dir <dir>`. The same implicit-preview
exit `3` and
explicit-dry-run exit `0` distinction applies at global scope.

If global Claude Code discovery reaches a Claude home that is not marked as
AgentKit-owned, the update refuses the foreign-home takeover before any emitter
or ownership mutation. The command may still print a snapshot ID because it
takes recovery material before this check; that ID does not mean a partial write
occurred. Confirm that the discovered home is the intended global install, then
run `ak kit init <kit> --global` to re-establish ownership before refreshing.
Do not restore the snapshot solely because this refusal printed it.

<Callout type="info">
  `ak update --global` reports Claude Code user-plugin-only installs instead of
  silently refreshing them. Refresh that delivery mode explicitly with
  `ak kit refresh engineer --global --switch-to-plugin`.
</Callout>

## Refresh a specific install route

Use `ak kit refresh` when you need to preserve an existing target, scope, or
Claude Code delivery route exactly:

```bash
ak kit refresh engineer --target codex --channel stable --yes
ak kit refresh engineer --global --switch-to-plugin --channel stable --yes
```

Refresh creates a recovery snapshot, rewrites current AgentKit output, removes
stale generated and owned paths only while ownership evidence still matches,
and preserves the previous selected-skill subset. Modified, unsafe, linked, and
shared paths remain in place. Review the confirmation preview; avoid
`--no-backup`.

## Verify the update

After updating:

1. Run `ak --version` and confirm the channel/version you intended.
2. Review the update summary for skipped or preserved files.
3. Reopen each affected runtime.
4. Invoke one important installed skill in each updated target.

If the Kit requires a newer CLI, update `ak` on the same channel first, then
repeat the Kit preview.

When you filter follow-up diagnostics, `ak doctor --adapter` accepts only
`claude-code`, `codex`, and `cursor`, which have dedicated doctor suites. Any
other adapter value is invalid and exits `2` instead of returning an empty
successful check set.

## If the expected files did not change

Work through the route before forcing another write:

1. Confirm the layer: `ak self-update` changes only the CLI binary, `ak update`
   handles AgentKit-owned project content, and `ak kit refresh` re-emits one
   installed runtime route.
2. Compare both the CLI version and the resolved Kit version/channel with the
   versions you expected.
3. Match the original target, project or global scope, and Claude Code native or
   plugin delivery mode. A different route writes to a different destination.
4. Check whether the file belongs to the previously selected Skill subset.
5. Review the preview and ownership evidence. A user-modified, unknown, linked,
   or shared path may be preserved intentionally even when the operation
   succeeds. A `refusing foreign-home takeover` error instead stops before
   mutation; follow its exact `ak kit init <kit> --global` recovery command.

See [How installation and refresh work](./installing-kits#predict-lifecycle-changes)
for the ownership classes, reconciliation rules, and worked before/after model.
Do not delete an entire runtime directory to make a refresh appear successful.

## Recover a kit update

Keep the snapshot ID and recovery path printed by the operation. Inspect a
snapshot before restoring it:

```bash
ak backups list
ak backups show <id>
ak backups verify <id>
ak recover <id> --dry-run
```

`ak recover` is an exact alias for `ak backups restore`. Restore is
replace-only: it overwrites captured files, removes only exact absent paths or
explicitly approved AgentKit plugin directories, and normally leaves unrelated
files created after the snapshot in place.

If `ak backups show <id>` lists project bundle roots, repeat every exact root in
the recovery command:

```bash
ak recover <id> --allow-root /absolute/project --dry-run
ak recover <id> --allow-root /absolute/project
```

When more than one root is listed, repeat `--allow-root` with every exact path
in both commands.

If the operation says the project snapshot is outside `ak backups restore`, use
the printed snapshot-files directory and copy back only the affected files.
Otherwise, apply the reviewed restore plan with `ak recover <id>` and confirm
the prompt. For a project bundle, retain every reviewed `--allow-root` flag in
that apply command.

Restore is not transactional across multiple files; an interruption can leave
an intermediate state. Preserve unrelated work and take a new snapshot before
rolling backward when practical. Do not recover `--latest` blindly, delete an
entire runtime directory, or rerun the failed update with `--force` before you
understand the current state. Declining restore exits `3`, a held backup lock
exits `4`, an invalid or missing snapshot exits `5`, and other failures exit
`1`.
