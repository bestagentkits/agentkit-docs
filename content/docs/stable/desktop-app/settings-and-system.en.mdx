The System group holds app-level configuration and maintenance: sending
feedback, editing settings, managing the local analytics index, designing a
status line, and migrating providers. After this page you will know what each
surface changes and what stays local.

## Send feedback safely

![Feedback form with a redacted preview panel](/gui/feedback-form.webp)

Feedback files a report in the AgentKit issue tracker. Fill in the type, title,
area, and description, optionally attach a redacted diagnostics summary, and
review the **Redacted preview** before submitting.

Feedback is sent only when you submit it. Preview the payload first, and never
include a license key, session file, or unmasked config value.

## Edit app settings

![Settings App tab showing appearance and runtime preferences](/gui/settings-app.webp)

Settings holds App preferences (appearance, theme, sidebar width), a config
editor, effective-config inspection, and the database tab. Theme changes apply to
this machine immediately; some preferences are marked as coming later.

Interface preferences are local Desktop state. The config editor changes AgentKit
configuration, so review effective values before saving.

## Manage the local analytics index

![Settings Database tab with the local analytics index controls](/gui/settings-database.webp)

The Database tab manages the local analytics index that backs the Dashboard. It
shows what is serving, the fact count, last success, and privacy, with
**Disable**, **Refresh**, **Rebuild**, and **Delete index** actions.

The index is optional, local-only, and disposable — nothing is uploaded.
Rebuilding recomputes it from supported session sources on this device.

## Read provider usage limits

The top-bar badge and popover show the same local usage-limit data as
[`ak usage limits`](../reference/cli/usage/limits) and the Dashboard's Usage
limits card. Open the badge, choose a provider (`claude`, `codex`, or `all`),
and read both rolling windows (`5h` and the trailing 7-day window) from the
local analytics index.

The badge itself reads as one of four states — `ok`, `warn`, `danger`, or
`stale`. By default the popover auto-refreshes every 60 seconds and rows carry
`raw_only` provenance: counts read straight from the local index, with no
fabricated quota percentage. The badge and popover stay empty until the
local index has counted usage; run
[`ak analytics enable`](../reference/cli/analytics/enable) first if you have
not opted in.

A cold or absent index returns zeroed windows together with an index state, so
the view explains the empty state instead of showing a misleading zero. Unless
you turn on advanced polling, nothing leaves this machine; rebuild the index
from the Database tab when the windows look stale.

### Advanced provider polling (experimental)

Advanced polling is off by default. When you turn it on, AgentKit asks each
enabled provider for its own usage percentages and adds them to the same rows.
The **Advanced polling** panel appears in Settings only when Desktop, or the
browser dashboard, was started with `AGENTKIT_ADVANCED_POLLING=1` in its
environment. Without that variable the panel stays hidden and polling cannot
be turned on.

Setting **Advanced provider polling** to **On** opens an acknowledgement
dialog. **Enable polling** stays disabled until you tick all three statements:

- The usage endpoints are undocumented, and polling them may be against the
  provider's terms of service.
- The provider can change or remove the endpoints at any time, and polling then
  stops working without notice.
- Polling may lead the provider to rate-limit, restrict, or suspend your
  account.

The acknowledgement is not remembered: turning polling off and on again shows
the dialog again, with every box cleared. While polling is on, the panel shows
when you last acknowledged. Turning polling off takes effect immediately.

While polling is on, the panel shows a switch for each provider (Claude Code
and Codex, both on by default) and a **Refresh interval** of 30 s, 60 s
(default), 2 min, or 5 min. The badge, popover, and Dashboard card refresh at
that interval. Between polls every surface reads the cached answer, and each
provider is capped at a burst of three requests a minute.

AgentKit reuses the access token the official CLI already stored. It never
requests, refreshes, or writes a token.

| Provider | Endpoint | Token lookup order |
| --- | --- | --- |
| Claude Code | `GET https://api.anthropic.com/api/oauth/usage` | `ANTHROPIC_OAUTH_TOKEN`, then `.credentials.json` in `CLAUDE_CONFIG_DIR` or `~/.claude`, then the `Claude Code-credentials` item in the macOS keychain |
| Codex | `GET https://chatgpt.com/backend-api/wham/usage` | `OPENAI_SESSION_TOKEN`, then `auth.json` in `CODEX_HOME`, `~/.codex`, or (outside Windows) `codex` under `XDG_CONFIG_HOME` or `~/.config` |

On macOS, the first fetch asks you to allow access to the Claude Code keychain
item. If you deny it, Claude keeps showing local counts and polling stays on;
allow access later from Keychain Access, or set `ANTHROPIC_OAUTH_TOKEN`
instead.

Rows the provider answered switch to `provider_reported` provenance and show
the provider's used percent; the local token counts stay. When a poll fails,
the rows keep their local counts and show the reason, such as a missing or
expired token, a rate limit, or an endpoint error. A provider that has answered
before keeps serving its last values, marked stale. If the provider rejects the
stored token, AgentKit switches polling off for that provider and marks it
auto-disabled; refresh the token in Claude Code or the Codex CLI, then turn the
provider back on. A build compiled without advanced polling keeps showing local
counts.

These settings live under `usage_limits` in the AgentKit config
(`~/.agentkit/config.yaml`) and are shared with
[`ak usage limits`](../reference/cli/usage/limits), which uses provider
figures only when it also runs with `AGENTKIT_ADVANCED_POLLING=1`.

## Review Skill and agent insights

The Insights page reads that same local evidence store: collect bounded native
sources, record outcome evaluations, compare a baseline against a candidate, and
inspect the evidence behind one record. Consent for collection and sharing is
explicit and separate from local evidence, and a monthly contribution is frozen
and privacy-filtered on this machine so you review the payload before sending
it. Leaving consent unset keeps every insight local.

## Design a status line

![Status line designer with themes, sections, and a live preview](/gui/status-line-designer.webp)

The Status Line designer builds a Claude Code status line by drag-and-drop: pick
a color theme, set context-window and usage-quota thresholds, and arrange the
Model, Directory, Git, Cost, and other sections across lines with a live preview.
Save writes the status-line configuration.

## Migrate providers

![Migrate wizard discovering migration sources](/gui/migrate-wizard.webp)

The Migrate wizard moves a Claude Code stack toward other providers across four
steps — Discover, Reconcile, Execute, and Summary. Discover lists migration
sources (such as `~/.claude`, `~/.claudekit`, and `~/.agentkit`) with file counts
and sizes so you choose what to include.

Review each step before executing, because migration changes provider setup on
this device.
