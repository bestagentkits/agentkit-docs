---
title: Run a software delivery workflow
description: Chain Engineer Skills for feature delivery, bug repair, and UI implementation with explicit review and verification gates.
---

Use this guide when the deliverable is a tested software change. Choose the
smallest recipe that covers the work, invoke one Skill at a time, and carry only
reviewed outputs forward.

## Before you start

Confirm the repository, target behavior, constraints, non-goals, acceptance
checks, and authority boundary. Read [Runtime adapters](../../concepts/runtime-adapters)
if the chain depends on Agents, Hooks, browser control, or another
runtime-specific capability.

## Deliver a feature

1. Use [ak:help](../engineer/skills/help) when you do not know the starting
   Skill. Skip it when the workflow is already clear.
2. Use [ak:brainstorm](../engineer/skills/brainstorm) to compare viable
   directions, identify load-bearing assumptions, and select one outcome.
3. Use [ak:scout](../engineer/skills/scout) or
   [ak:research](../engineer/skills/research) to resolve repository or external
   evidence gaps that affect the decision.
4. Use [ak:plan](../engineer/skills/plan) to turn the accepted direction into
   phases, risks, dependencies, acceptance checks, and stop conditions.
5. Use [ak:cook](../engineer/skills/cook) to implement the approved scope.
6. Use [ak:test](../engineer/skills/test) for independent verification, then
   [ak:code-review](../engineer/skills/code-review) for production-risk review.
7. Use [ak:ship](../engineer/skills/ship) only after the branch and its evidence
   are ready for the repository handoff process.

Start with a request such as:

> Compare implementation approaches for the accepted outcome. Preserve the
> stated non-goals, identify the assumption each approach depends on, and stop
> before implementation.

Pass the selected direction and evidence into ak:plan. Pass the approved plan
path, current repository state, and authority limits into ak:cook.

## Repair a bug

1. Use [ak:debug](../engineer/skills/debug) to reproduce the symptom, collect
   evidence, narrow the failing boundary, and prove a root cause.
2. Use [ak:fix](../engineer/skills/fix) with the proven cause and a narrow repair
   boundary.
3. Use [ak:test](../engineer/skills/test) to rerun the reproduction, regression
   checks, and affected test family.
4. Use [ak:code-review](../engineer/skills/code-review) to inspect the final diff
   for production risk and incomplete edge cases.

Do not move from debug to fix when the output contains competing causes or an
unreproduced symptom. Return to evidence collection instead.

A useful repair handoff includes the reproduction, expected and actual result,
root-cause evidence, affected files, rejected causes, safety boundary, and the
checks that must turn green.

## Deliver a UI change

1. Use [ak:frontend-design](../engineer/skills/frontend-design) to convert the
   brief or visual reference into an accepted interaction and visual direction.
2. Use [ak:frontend-development](../engineer/skills/frontend-development) to
   implement the scoped React or TypeScript change using existing project
   conventions.
3. Use [ak:web-testing](../engineer/skills/web-testing) to verify the real page
   at the required desktop and mobile viewports.
4. Use [ak:code-review](../engineer/skills/code-review) to review accessibility,
   responsive behavior, state handling, and production risk.

Carry the target URL, viewport matrix, interaction states, reference assets,
accessibility constraints, and accepted visual differences between Skills.
Visual similarity alone is not completion; verify interaction and console
behavior too.

## Stop and resume safely

Stop the workflow when a prerequisite is missing, implementation exceeds the
approved plan, a test fails, review finds a blocker, or merge/deploy requires
new authority. Record the failed gate and use
[ak:handoff](../engineer/skills/handoff) before another session or owner
continues.

The workflow is complete when the accepted outcome is implemented, required
checks pass, review findings are resolved or explicitly accepted, and the
handoff identifies every remaining external action.
