Use `ak:bootstrap` to take a new project from an accepted outcome to running
code. The Skill coordinates research, stack selection, design, implementation,
testing, code review, UX/AI-experience enhancement, and onboarding instead of
leaving you with an unexplained scaffold. There is no separate planning phase:
the locked brainstorm contract goes straight to `ak:cook`, which sizes its own
implementation plan.

## Choose ak:bootstrap for a new project

### Use ak:bootstrap when

- You are starting a project or full-stack setup from scratch.
- You can state the product outcome, constraints, non-goals, and observable
  acceptance criteria, or you want `--ask` to interview you until they are locked.
- You want stack and design decisions connected to a tested implementation.
- You are prepared for the selected mode to create project files and
  documentation.

### Choose another workflow when

- You are changing an existing project with a known scope. Use `ak:cook`.
- You still need to compare product directions. Use `ak:brainstorm` first.
- You only need an implementation plan. Use `ak:plan`.
- You need to expose existing code as a CLI or MCP server. Use `ak:agentize`.

## Prepare the project and runtime

Before you start:

- Complete [Onboarding](../../../getting-started/onboarding), and confirm
  Engineer Kit is installed for the runtime and scope you are using.
- Open the directory that will own the new project.
- Decide whether Git may be initialized if the directory is not already a
  repository.
- State any required stack, compatibility, security, delivery, and licensing
  constraints before automatic selection begins.
- Keep credentials out of the request. Provide them later only through the
  project's approved setup flow.

| Runtime | Invocation | Availability boundary |
| --- | --- | --- |
| Claude Code | `/ak:bootstrap ...` | Native delivery is the default; explicit plugin delivery is also supported. The workflow can use the full supported Claude collaboration surface. |
| Cursor | `/ak:bootstrap ...` | Slash invocation follows the user-verified Engineer Skill spelling. Agent, plan, and approval capabilities depend on the live Cursor surface. |
| Codex | `$ak:bootstrap ...` | Native Skill discovery is supported. Delegated or parallel phases require the current Codex session to expose the needed multi-agent capabilities. |

See [Runtime adapters](../../../concepts/runtime-adapters) before assuming that
the same orchestration controls exist in every runtime.

If you omit a mode flag, the Skill uses `--auto`.

| Mode | What it changes | Approval behavior |
| --- | --- | --- |
| `--auto` (default) | Runs research, stack selection, and design automatically, then hands the contract straight to `ak:cook --auto` | Keeps the opening contract gate and stops only at an authorization boundary (a missing secret, an unauthorized destructive or outward-facing action, or uncovered spend) |
| `--full` | Refines requirements, then asks before tech stack and design when you have not already stated a preference | Asks about a missing material decision at each of those steps; continues within the accepted scope through `ak:cook` |
| `--fast` | Runs research, stack, and design research in one parallel batch with no design gate, then a concise plan inside `ak:cook --fast` | Keeps the opening contract and normal `ak:cook` verification and safety gates |
| `--parallel` | Builds a dependency graph and assigns non-overlapping implementation ownership inside `ak:cook --parallel` | Keeps the opening contract; asks only about a missing material decision |

`--ask` is not a mode; it changes only how the opening brainstorm gate closes.
It activates `ak:advise` to interview you one question at a time until the
outcome, scope, constraints, non-goals, acceptance criteria, and definition of
done are locked and confirmed, then continues in the selected mode. Without
`--ask`, `--auto` decides each gap itself from your prompt, project
instructions, and the existing workspace, and records each choice as an
assumption; `--full`, `--fast`, and `--parallel` ask only about a decision that
would materially change the product or safety.

`--yagni` composes with every mode. It opts into challenging and cutting scope
that is not needed for the stated outcome; without it, the Skill scaffolds the
full requested scope and adds nothing unrequested. The flag is passed through
to `ak:cook` and `ak:code-review` so the choice survives each handoff.

`--ultra` composes with every mode, including `--parallel`. It makes the code
review phase run `/ak:code-review codebase --ultra` (including the re-review
after UX/AX enhancement), which uses code review's best-of-5 candidate
dispatch, verification, and evidence-validated union finalizer. `ak:cook` and
`ak:enhance-ux-ax` still run with their mode-appropriate flags. Never pair
`--ultra` with code review's `codebase parallel`, which that Skill treats as a
hard stop.

## Describe the project clearly

A useful request includes:

- **Outcome:** State what a user can do when the project is running.
- **Constraints:** Name required technologies, platforms, compatibility,
  security rules, and delivery boundaries.
- **Non-goals:** Exclude adjacent features that should not enter the first
  implementation.
- **Acceptance criteria:** Give observable checks for the main path, failure
  behavior, and important edge cases.
- **Authority boundary:** State whether Git initialization, dependency
  installation, external research, asset generation, commits, publication, or
  deployment are allowed.
- **Definition of done:** Say whether the brief names a live target
  (production, a store, a registry); the project is done only after it is
  released there and verified the way a real user or client reaches it.

The incident-response example should also say who may view incidents, which
events enter the audit log, what "private" means, and which validation proves
the first usable release.

## Understand the workflow

1. **The Skill locks the project contract.** It captures or reuses the
   outcome, constraints, non-goals, acceptance criteria, and definition of
   done, checking each surface the project has (web, mobile, CLI, API, MCP,
   WebMCP, library) against `references/project-brief-checklist.md`.
2. **The Skill checks Git state.** It inspects the actual destination and
   reuses an existing project and branch conventions rather than
   re-scaffolding or resetting it; it initializes Git only for a new project
   when the brief includes it.
3. **The Skill researches and selects the setup.** The depth, parallelism, and
   approval gates follow the chosen mode.
4. **The Skill creates design evidence when applicable.** It can produce design
   guidance, wireframes, screenshots, and generated assets through available
   design and media tools. A project without a visual interface designs its
   interface contract (commands, routes, tool schemas, public API) instead.
5. **The Skill implements through ak:cook.** There is no separate planning
   phase; the brainstorm contract plus the research, stack, and design outputs
   go straight to `ak:cook` with the mode-appropriate flag, and cook sizes its
   own implementation plan and runs the tests.
6. **The Skill runs code review.** `ak:code-review` reviews the new project
   (`--ultra` when bootstrap received it); blocking findings go back through
   `ak:cook` with the same mode flag until review passes.
7. **The Skill enhances UX and AX for a web surface.** When the project has a
   website or web app, `ak:enhance-ux-ax --auto` runs after code review passes
   and its changes are reviewed the same way; it is skipped and reported for a
   CLI, API, MCP server, or library.
8. **The Skill releases and verifies live, when the contract calls for it.**
   When the accepted contract includes a release or names a live target, the
   Skill provisions what the brief authorizes, releases through the pipeline,
   and verifies each surface the way a real user or client reaches it.
   Otherwise it reports the project as verified locally only.
9. **The Skill finishes the project handoff.** It evaluates documentation,
   updates plan state, guides onboarding, and reports changed files, checks,
   risks, and next actions.

## Keep approval and safety with you

<Callout type="warn" title="Automatic and parallel modes can change repository state">
  `--auto`, `--fast`, and `--parallel` proceed without a routine approval pause
  once the opening contract is locked. Use `--full` or `--ask` when a decision
  needs review before it is made.
</Callout>

Automatic execution does not grant unrelated authority. External research,
asset generation, dependency installation, credential use, commits, pushes,
publication, and deployment still depend on the tools available and the scope
you approved. The release and live-verification phase runs only when the
contract calls for it, and provisioning, staging, and production release stay
separate approval points within it.

Parallel mode requires exclusive file ownership and explicit dependencies.
Separate workers or worktrees reduce edit collisions; they do not provide an
operating-system sandbox or make conflicting changes safe to merge.

## Verify the result

A complete run should provide:

- A runnable project that matches the accepted outcome and non-goals.
- Stack and design decisions recorded in the project's documentation where
  they materially affect future work.
- Real tests and project checks, with failures resolved or reported.
- A code-review result with no hidden critical finding.
- For a web surface, an `ak:enhance-ux-ax` result against its DONE contract, or
  an explicit note that the project has no web surface.
- Onboarding steps for configuration that still requires you.
- A concise final report with changed files, validation, remaining risks, the
  definition of done and whether it was met, and unresolved questions.

Treat generated wireframes or a passing build as intermediate evidence. The
project is complete only when the acceptance criteria, tests, review, UX/AX
enhancement (for a web surface), and onboarding path agree.

## Troubleshoot or continue

| Symptom | Safe next step |
| --- | --- |
| The Skill asks about the product before setup | Supply the missing outcome, constraint, non-goal, or acceptance criterion. Every mode keeps this opening gate. |
| The wrong stack is being selected | Stop before approval, add the missing compatibility or delivery constraint, and rerun the affected decision. |
| Parallel work overlaps | Stop the writers, separate file ownership or sequence the dependent phases, then verify the integrated tree. |
| A design or external tool is unavailable | Keep the limitation visible and choose a supported local alternative or skip that optional output with an explicit decision. |
| Tests fail near the end | Keep the failure visible and return to implementation or debugging; do not label the scaffold complete. |
| A blocking code-review or UX/AX finding survives three fix attempts | Stop and report with evidence instead of continuing past the review or enhancement gate. |
| The runtime does not recognize the Skill | Confirm target and scope, start a fresh runtime session, then follow [Runtime cannot find a Skill or Agent](../../../troubleshooting/runtime-cannot-find-skill-or-agent). |

Continue with [Installing kits](../../../guides/installing-kits), the
[Engineer Kit overview](../../engineer), or `ak:cook` when the project already
has an accepted implementation scope.

## Know the current limits

- The Skill depends on the planning, implementation, testing, review, design,
  and media capabilities actually available in the active runtime.
- Dependency and asset tools may require network access or provider setup; the
  workflow cannot manufacture missing credentials or service availability.
- `--fast` reduces research overhead, not implementation verification.
- `--parallel` helps only when work can be split into independent ownership.
- UX/AX enhancement and live verification run only for the surfaces and
  release targets the accepted contract actually names.
